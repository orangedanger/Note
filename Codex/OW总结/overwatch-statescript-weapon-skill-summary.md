# 《守望先锋》网络脚本化的武器和技能系统：中文摘要

来源：[《守望先锋》网络脚本化的武器和技能系统](https://www.lfzxb.top/ow-gdc-weapon-and-skillsystem/)

原主题：GDC 2017，Dan Reed 分享《守望先锋》中用于武器和技能的网络脚本系统 `Statescript`。

## 一句话概括

《守望先锋》为武器、技能、表情、地图交互和局内模式实现了一套可视化状态脚本系统 `Statescript`：它让策划能以声明式方式搭建复杂玩法，同时由引擎自动处理服务器权威、客户端预测、回滚前滚、状态复制和带宽优化。

## 解决的问题

《守望先锋》的英雄、武器和技能差异很大，如果每个需求都由程序员手写 C++，迭代速度会跟不上设计需求。团队希望有一套系统能做到：

- 非程序员也能搭建高层 Gameplay 逻辑。
- 脚本开发者可以定义状态和状态转移，而不只是响应黑盒事件。
- 常见玩法能力能模块化复用。
- 网络同步状态机不需要每次手写。
- 系统能深度嵌入引擎、ECS、资源系统和网络层。

核心判断是：武器和技能不是孤立功能，而是一批可组合、可复用、可同步的状态机。

## Statescript 是什么

`Statescript` 是暴雪自研的可视化脚本语言。每个脚本是一张由节点组成的图，运行时会创建脚本实例，并挂在某个 ECS 实体上。

常见使用场景包括：

- 英雄武器，例如猎空的脉冲枪。
- 英雄技能，例如猎空闪回、卢西奥加速/治疗光环。
- 控制效果，例如被闪光弹命中后禁用移动和瞄准。
- UI、表情、局内规则、地图实体等。

脚本实例可以动态添加和移除；同一个实体上也可以同时存在同一个脚本的多个实例。

## 节点模型

`Statescript` 的基本节点包括：

- `Entry`：脚本入口，或等待某个消息后触发。
- `Condition`：控制流程分支。
- `Action`：一次性的 C++ 函数调用，执行后继续向后触发。
- `State`：持续存在的行为，激活后保持运行，直到自己结束或被外部关闭。

其中 `State` 是最重要的抽象。每种 `State` 背后都是一个 C++ 类，通常提供：

- `OnActivate`
- `OnDeactivate`
- `OnTick` / `OnFrameTick`
- `OnDependencyChange`
- 定时事件回调
- 网络同步和回滚辅助接口

这让脚本图的节点既能给策划使用，又能由程序员用 C++ 实现底层能力。

## 变量、属性与依赖

`Statescript` 支持两类变量：

- 实例变量：只属于某个脚本实例。
- 所有者变量：属于实体，可被该实体上的多个脚本实例共享。

例如武器子弹数可以是某个武器脚本的私有变量，而 `AbilityLock` 这类状态可以作为英雄实体的共享变量。

节点行为由属性驱动。属性的值来自 `Config Vars`，它们可以是：

- 字面量。
- 变量引用。
- Utility 函数。
- 表达式。
- 嵌套配置项。

系统还有依赖监听机制。`State` 可以监听变量或外部组件的数据源，当依赖变化时收到通知，而不是每帧主动轮询。这降低了运行时开销，也让声明式逻辑更自然。

## Subgraph、容器与生命周期

`Subgraph` 允许一个 `State` 激活或关闭一组子节点。一个常见例子是布尔开关状态：条件为真时激活一条子图，条件为假时激活另一条子图。

容器可以标记节点分组，也可以区分客户端专用和服务器专用逻辑。虽然系统目标是尽量隐藏网络细节，但在 UI、本地表现、服务器校验等场景中，仍然需要这种显式拆分能力。

生命周期是 `Statescript` 的核心主题：

- `State` 关闭时必须清理自己创建的动画、特效、变量修改和子图。
- 脚本实例删除时关闭所有状态。
- 实体销毁时删除所有脚本实例。
- 游戏结束时销毁所有实体。

这套清理契约减少了“对象还活着但不该活着”的 bug。

## 声明式与指令式混合

`Statescript` 同时支持声明式和指令式逻辑。

声明式逻辑表达“只要条件成立，这些状态就应该激活”；指令式逻辑表达“先做 A，再等待，再做 B”。文章认为，复杂需求的主体更适合声明式，因为它天然匹配状态生命周期和最终一致性的网络模型；指令式则适合放在叶子节点或短流程里。

示例中给死神添加一个右键技能：

- 按住右键 1 秒后进入准备状态。
- 切换第三人称视角。
- 松开右键后，如果准备完成，就把角色发射到空中。
- 如果按住不到 1 秒，则不发生效果。

这个例子展示了声明式状态和指令式动作的组合。

## C++ 运行时结构

运行时基于固定 `Command Frame`，每帧约 16ms，也就是 60 帧每秒。每个实体需要挂载 `Statescript` 组件才能运行脚本。

组件中主要保存：

- 内部命令帧 `Internal Command Frame`。
- 脚本实例数组。
- 所有者变量。
- 同步管理器 `Sync Manager`。
- 事件队列。
- 实例变量。
- 每个脚本实例的唯一 ID。
- 指向图资源的静态数据。
- 已创建的 `State` 对象数组。

图资源使用结构化数据 `Stu` 定义。`Stu` 能生成资源、编辑器、编译器和运行时都能理解的类型信息；节点属性、约束和插头也通过这种方式描述。

## 网络化 Statescript 的目标

网络系统需要满足五个目标：

- 可用性：脚本开发者不用关心底层网络细节。
- 响应性：玩家按键、开火、放技能必须立刻有视觉反馈。
- 安全性：客户端不能直接决定游戏结果，服务器保持权威。
- 效率：弱网络、高延迟、丢包环境下仍要可用。
- 无缝：尽量隐藏回滚、复制和纠错带来的卡顿或视觉抖动。

团队的做法是：服务器和客户端运行逻辑上相同的同步实例，客户端可以先做预测表现，服务器随后确认；如果预测错了，客户端在同一帧内回滚、复制服务器状态，再前滚回当前时间。

## 同步实例与非同步实例

同步实例包括：

- 武器。
- 技能。
- 表情。
- 局内模式。
- 地图实体，例如门、血包等。

非同步实例包括：

- 菜单。
- 英雄收藏品。
- 局末流程。
- 音乐。

同步实例和非同步实例之间仍然可以互发消息。例如局内模式脚本可以控制音乐脚本。

## Local 与 Remote

对某个客户端来说：

- 本地玩家直接控制的实体是 `Local`。
- 其他网络实体是 `Remote`。

`Local` 实体需要预测、回滚和前滚，因为玩家要立即感到输入生效。`Remote` 实体通常不完整模拟同步脚本，只复制服务器下发的状态，并轮询少量需要刷新的状态。

这一区分是带宽和性能优化的基础。

## 服务器权威与输入上行

`Statescript` 网络模型是服务器权威。通常只有服务器向客户端下发状态，客户端发给服务器的主要是：

- 按键输入。
- 瞄准数据。

客户端输入需要发往未来的命令帧，而不是当前已收到的服务器帧。服务器根据 RTT 和网络波动告诉客户端应该提前多少帧发送输入，以便输入能及时到达服务器并被处理。

## 服务端同步：Delta、Ghost、Packet

服务器每个命令帧收集客户端输入，模拟所有实体，把变化记录为 `StatescriptDeltas`，再发送给客户端。

三个关键数据结构：

- `StatescriptDeltas`：记录某个实体在特定命令帧发生的变化，包括实例创建/销毁、变量变化、State 变化、Action 执行、所有者变量变化等。
- `StatescriptGhosts`：记录每个客户端已经知道某个实体的哪些帧，以及哪些数据包还在传输中。
- `StatescriptPackets`：实际发送的 payload，可以由一段命令帧范围内多个 Delta 的并集生成。

如果发生丢包，服务器可以发送多个 Delta 的并集，帮助客户端从丢包中快速恢复，而不必重传每一个中间状态。

## 客户端同步：复制、回滚、前滚

客户端收到服务器包后：

- 如果是过期、重复或乱序数据，直接忽略。
- 如果是 `Remote` 实体，直接复制服务器状态。
- 如果是 `Local` 实体，先回滚已执行的预测，再复制服务器状态，然后用缓存的输入重新模拟到当前帧。

这个过程叫 `Rollback` 和 `Roll Forth`。它通常在同一帧内完成，玩家不应该察觉。

不过这对节点实现提出了额外要求。比如音效、特效、UI 不能因为回滚和前滚而重复播放或闪烁。为此 `State` 和 `Action` 提供了辅助机制：

- 激活/关闭原因参数。
- 当前模拟阶段查询。
- `OnBecomeActiveThisTick` / `OnBecomeInactiveThisTick`。
- 临时回滚存储。
- 自动复制 State 内部数据的结构化镜像数据库。

这些机制让 C++ 程序员更容易写出可预测、可回滚的节点。

## 哪些历史数据需要准确

在回滚和前滚期间，并不是所有数据都需要历史版本。

需要历史数据的通常包括：

- `Local` 实体的变量和状态。
- 按键输入。
- 瞄准数据。
- 所有实体的位置和姿态。

位置和姿态尤其重要，因为技能是否命中、能否释放，经常取决于实体之间过去某一刻的相对关系。

不一定需要历史数据的包括：

- `Remote` 实体变量和状态。
- 血量、过滤器等其他组件的最新状态。

过度使用历史版本反而可能增加预测错误。

## 带宽与性能优化

为了降低带宽，`Statescript` 在编译脚本时自动分析同步需求。

对 `Local` 实体，下发内容必须尽可能完整，因为客户端要精确预测和回滚。

对 `Remote` 实体，优化空间更大：

- Remote 不完整模拟同步脚本。
- Remote 只持有需要轮询的激活 State。
- 没有标记为需要同步的节点会被裁剪。
- 数据包只包含 Remote 需要的 State、Action 和变量。

节点类型可以通过属性声明是否需要同步给 Remote，例如 `SYNC_ALL`。编译器通过反射分析图资源和节点引用的变量，生成每个脚本对象对应的同步协议。

结果是：Remote 客户端执行节点更少、变量更少、带宽更低，客户端性能也更好。

## 收益

这套系统带来了几个主要收益：

- 快速迭代：新英雄从原型到上线，很多时候不需要改 C++。
- 节点复用：早期英雄需要很多新节点，后期英雄越来越多地复用已有节点。
- 自动同步：程序员很少需要手写状态机同步代码。
- 生命周期 bug 更少：清理和销毁逻辑集中在状态生命周期契约里。
- 网络一致性更稳定：同步、回滚和前滚由核心系统统一处理。

从团队角度看，Statescript 把策划从大量工程等待中解放出来，也让工程师把精力更多放在底层节点和基础能力上。

## 代价与挑战

这套系统并不便宜。

主要代价包括：

- 运行时、编辑器、编译器、调试器和 Sync Manager 都需要长期投入。
- 程序员和策划都要学习声明式状态机思维。
- 必须判断某个特性应该放在脚本里，还是写成 C++ 节点。
- 复杂节点拆分过度会引入额外复杂性。
- 最终一致性的状态复制不保证同步每个中间步骤，有时需要临时方案。

文章中的一个典型问题是“顺序”导致的表现 bug：秩序之光右键蓄力释放时，服务器一帧末尾复制变量和 State，Remote 客户端因为变量先被复制为 0，导致抛射物视觉缩放错误。修复方式是额外保存客户端表现所需的视觉缩放变量。

这说明：基于状态的最终一致性模型很强，但不是魔法。个别对事件顺序敏感的表现仍需要额外设计。

## Q&A 中的补充观点

- 复杂循环或性能敏感逻辑更适合 C++，例如射线检测不适合每帧放在脚本里跑。
- 二进制脚本资源合并困难，团队通过资源独占签出和拆成小脚本缓解。
- Statescript 从 Titan 时期就开始使用，Overwatch 之前已经有原型。
- 客户端回滚代价不低，但主要只发生在 Local 实体上。
- Server-only / Client-only 节点虽然违背“隐藏网络细节”的理想，但 UI、本地表现等场景确实需要。
- 系统高度依赖暴雪的资源系统、网络层和结构化数据，可移植性不强。
- 大多数新英雄 Gameplay 逻辑可以用脚本完成；新的底层能力才需要 C++ 节点。
- 部分技能可以阻止服务器倒带，例如逃生技能用于保护被攻击者体验。
- 调试器记录实体历史，可以在服务器/客户端视图之间切换并单步追踪。

## 可迁移到其他项目的原则

1. 可视化脚本系统真正有价值的地方，不是“能连节点”，而是能统一处理状态生命周期、网络同步和调试。
2. 给策划的脚本语言应该提供“定义状态”的能力，而不只是响应事件。
3. 复杂实时网络游戏最好把预测、回滚、复制和前滚做成系统级能力，而不是每个技能手写。
4. `Local` 与 `Remote` 的同步策略应该不同；本地预测需要完整数据，远端表现可以裁剪。
5. 编译期分析同步需求，比运行时临时判断更稳定，也更节省带宽。
6. 声明式状态机适合最终一致性网络模型，因为它关注“现在应该处于什么状态”。
7. 自动化同步不能消除全部问题，特别是对事件顺序敏感的视觉表现仍要单独处理。
8. 自研脚本系统只有在项目规模、内容迭代需求和网络复杂度足够高时才值得。

## 术语速记

- `Statescript`：守望先锋自研的可视化状态脚本系统。
- `Entry`：脚本入口或消息触发入口。
- `Condition`：流程条件节点。
- `Action`：一次性动作节点，通常是 C++ 函数调用。
- `State`：持续行为节点，有生命周期。
- `Subgraph`：由某个 State 激活或关闭的子图。
- `Config Var`：为节点属性提供值的配置变量。
- `Owner Variable`：实体级共享变量。
- `Instance Variable`：脚本实例私有变量。
- `Command Frame`：固定时间步下的命令帧。
- `Internal Command Frame`：客户端内部模拟帧。
- `Sync Manager`：负责 Statescript 同步、复制、回滚和前滚的管理器。
- `Delta`：某个实体在某个命令帧发生的状态变化。
- `Ghost`：服务器记录某客户端已知状态范围的数据结构。
- `Packet`：发送给客户端的同步数据包。
- `Local`：当前客户端直接控制的实体。
- `Remote`：当前客户端观察到的其他实体。
- `Rollback`：回滚客户端预测。
- `Roll Forth`：使用缓存输入重新模拟到当前帧。
- `SYNC_ALL`：标记节点需要同步给 Remote 客户端的属性。

## 个人整理版结论

这篇分享最重要的启发是：脚本系统、状态机和网络同步不能分开看。对于《守望先锋》这种英雄机制极多、响应要求极高的在线动作游戏，真正难的是让内容团队能快速迭代，同时仍然保住服务器权威、弱网恢复、带宽控制和调试能力。

`Statescript` 的价值在于把这些复杂度封装成一套工作流：策划用图表达状态，程序员提供可复用节点，编译器分析同步需求，运行时负责预测和回滚，调试器记录历史。代价很高，但对于内容密集型 3A 多人游戏，这种投入换来了长期迭代效率。
