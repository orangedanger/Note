# 《守望先锋》架构设计和网络同步：中文摘要

来源：[《守望先锋》架构设计和网络同步](https://www.lfzxb.top/ow-gdc-gameplay-architecture-and-netcode/)

原主题：GDC 2017，Tim Ford 分享《守望先锋》的 Gameplay 架构与网络同步设计。

## 一句话概括

《守望先锋》用一套严格约束的 ECS 架构，把复杂的英雄玩法、预测、回滚、命中判定和网络同步拆成低耦合的 System 与 Component，从而在高延迟、丢包和大量英雄机制并存的情况下，仍然保持快速响应和可维护性。

## 核心问题

《守望先锋》是一款在线团队英雄射击游戏，复杂度主要来自两方面：

- 英雄差异极大，每个英雄都有独特技能、移动方式、武器和状态。
- 作为 FPS/动作游戏，玩家输入必须立即得到反馈，但服务器又必须保持权威，不能信任客户端。

因此架构目标不是“让代码看起来漂亮”，而是降低不断增长的 Gameplay 代码复杂度，让大量系统可以协作，同时避免模块之间互相调用、互相依赖、互相污染。

## ECS 架构设计

文章中的 ECS 可以理解为：

- `World`：包含所有实体和所有 System。
- `Entity`：本质是一个 ID，代表一组组件的集合。
- `Component`：只存储状态，不包含行为。
- `System`：包含行为，不保存业务状态。

System 遍历自己关心的 Component 组合，只处理这一个“切片”。它不关心实体到底是玩家、机器人、子弹、门还是平台，只关心这个实体是否拥有它需要的组件。

这种设计把“对象是什么”弱化了，把“哪些状态被哪些行为处理”强化了。传统 OOP 往往把状态和行为绑在一个类里，但在复杂游戏里，同一个组件可能被多个系统以不同视角使用。例如 `Connection` 既可能用于 AFK 检测，也可能用于网络广播、玩家名称显示、战绩统计等。如果把行为塞进 `Connection.Update()`，很快就会不知道新逻辑该放在哪里。

## 单例组件与 Killcam 重构

早期团队曾把一些全局状态放进 System，并通过全局指针访问。但 Killcam 需求暴露了问题：客户端需要同时存在两个 ECS World，一个用于实时游戏，一个用于回放。如果仍然依赖“唯一全局 System”，调用点会全部变得脆弱。

解决方案是引入 `Singleton Component`：

- 全局状态不再放在 System 中，而是放在只有一个实例的组件里。
- System 仍然保持无状态。
- 多个 System 可以通过 EntityAdmin 访问同一个单例组件。

例如输入状态从 `InputSystem` 中移出，放进 `SingletonInput`。`InputSystem` 只负责从操作系统读输入并填充状态；移动预测、命令打包等其他 System 读取同一个输入状态，各自完成自己的行为。

这个模式消除了很多 System 之间的直接依赖，也让“谁能修改关键数据”变得更清楚。

## Utility 函数与共享行为

当多个 System 都需要同一段行为时，文章建议使用 Utility 函数，但有严格限制：

- Utility 应尽量只依赖少量组件。
- Utility 最好只读数据，避免副作用。
- 如果 Utility 依赖很多组件，调用点就必须被严格限制。
- System 不应该调用其他 System 的函数。

例如判断两个实体是否敌对，可以作为纯 Utility：它只读取队伍、宠物主人、宠物等相关组件，返回敌对关系。这样很多 System 可以复用这段逻辑，而不会互相耦合。

## 延迟执行与副作用控制

文章反复强调：复杂度常常来自“副作用发生在太多地方”。

例如命中特效、弹孔、焦痕等碰撞效果，可能由 hitscan 子弹、抛射物、粒子光束、喷涂等多个系统触发。如果每个调用点都直接创建实体、管理资源、处理生命周期，就会出现大量分散副作用。

更好的做法是：

- 把请求写入队列或单例组件。
- 当前模拟阶段只记录“想发生什么”。
- 到帧内更合适的时机统一处理副作用。

这让副作用从“到处发生”变成“集中发生”，降低了测试和维护成本。

## 网络同步目标

网络同步的目标是：在服务器权威前提下，让玩家操作看起来立即响应。

需要预测的内容包括：

- 移动
- 技能
- 武器行为
- 命中判定中的部分视觉反馈

核心原则是：玩家按下按钮后，客户端必须马上表现结果，不能等待服务器回包。服务器稍后验证，如果客户端预测错了，再纠正。

## 确定性、命令帧与客户端预测

《守望先锋》使用固定时间步和量化帧来降低预测错误：

- 时间被切成固定的 `command frame`。
- 普通情况下每帧约 16ms。
- 电竞比赛环境下可以更短。
- 需要预测的 System 使用 `UpdateFixed`，按固定命令帧运行。

客户端总是领先服务器：大约领先半个 RTT 加上缓冲帧。玩家输入会先在客户端模拟，同时打包发送给服务器。服务器用稍后的权威模拟结果返回客户端。

客户端保存两类环形缓冲：

- 运动状态历史，用于和服务器快照比较。
- 输入历史，用于预测失败后的重放。

如果服务器返回的旧帧状态与客户端历史状态一致，客户端继续运行。如果不一致，客户端回滚到服务器确认的状态，再把之后保存的输入全部重放，前滚到当前时刻。

这就是“预测、校验、回滚、重放”的主流程。

## 丢包处理与时间膨胀

网络并不稳定，客户端输入包可能丢失。服务器会保留一个尽量小的输入缓冲。如果缓冲空了，服务器只能复制最后一次输入进行短暂预测。

为了减少丢包影响，客户端会：

- 发送输入滑动窗口，而不只是当前帧输入。
- 从服务器最后确认的帧开始，把之后所有输入一起打包。
- 当服务器检测到丢包或缓冲不足时，通知客户端加快模拟节奏。
- 网络恢复后，客户端再降低时间刻度，服务器缓冲也逐渐缩小。

这个机制的目标是：用输入冗余和动态缓冲，尽量填补丢包造成的空洞，减少预测错误，同时保持操作响应。

## 技能系统的预测与回滚

技能和移动采用类似机制：

- 客户端先预测技能状态。
- 服务器稍后权威验证。
- 如果预测错误，客户端回滚到服务器快照。
- 然后重放输入和技能状态，追上当前时刻。

这使得技能动画、特效、状态切换可以立即表现，同时仍然服从服务器权威。

## 命中判定与向后回溯

命中判定是文章中最复杂也最有价值的部分。

基本原则：

- 伤害不在客户端预测，因为客户端不可信。
- 命中相关的视觉反馈可以部分预测。
- 服务器最终决定是否真正命中、是否造成伤害。

为了让射击体验公平，服务器会根据攻击者开火时的时间，把目标倒回到当时的位置进行判断。这就是 `backwards reconciliation`。

`MovementState` 组件记录实体的运动历史。只要实体有相关运动状态，就可以在服务器判定命中前被回溯。目标不一定是玩家，也可能是门、移动平台、载具或护盾。

为了避免倒回所有实体，系统会先用逻辑边界筛选：某个目标过去一段时间的运动范围会形成一个包围体，只有射线与这个范围相交时，才需要对该实体做精确回溯。

高 Ping 下系统会降低预测程度。例如超过约 220ms 时，会延迟部分命中效果，等待服务器确认。原因是目标位置已经外插太远，继续预测会让受害者体验很差，例如明明已经躲到墙后却仍被打中。

## ECS 如何简化网络同步

ECS 的价值在于让网络同步只关心少量组件和 System：

- 有 `Connection` 的实体可以被识别为玩家控制对象。
- 有 `MovementState` 的实体可以被时间回溯。
- `ModifyHealthQueue` 负责延迟处理真实伤害。
- 网络输入输出集中在少数 Network System 中。

复杂问题没有消失，但影响范围被限制住了。网络同步不需要理解所有游戏对象，只需要识别组件组合。

## 最重要的工程原则

文章最后总结出的 ECS 约束非常关键：

- 组件没有函数。
- System 没有状态。
- 共享代码放到 Utility 中。
- 复杂副作用通过队列延迟处理，尤其是单例组件。
- System 不调用其他 System 的函数。

这些规则看似死板，但作用是减少“潜规则”和隐式耦合。越复杂的项目，越需要这种边界。

## 可迁移到其他项目的启发

1. 架构的核心不是模式本身，而是限制复杂度增长。
2. 状态和行为分离，可以让同一状态被多个系统以不同视角使用。
3. 全局状态不一定要放进全局服务，可以用单例组件纳入 ECS 世界。
4. 副作用要集中处理，尤其是创建实体、改血量、生成特效、发网络消息这类行为。
5. 网络同步要把“立即响应”和“服务器权威”分开：客户端先预测，服务器后确认。
6. 回滚重放要求模拟尽量确定性，因此固定时间步、输入历史和状态快照都很重要。
7. 高延迟时不能无限照顾攻击者，也要保护受害者体验。
8. 复杂系统需要清晰的读写边界，否则多线程、调试和扩展都会变得困难。

## 术语速记

- `ECS`：Entity Component System，实体组件系统。
- `Entity`：实体 ID，本身不携带行为。
- `Component`：状态数据。
- `System`：处理组件状态的行为逻辑。
- `Singleton Component`：只有一个实例的组件，用来保存全局或共享状态。
- `Utility`：可复用的共享行为函数，最好少依赖、少副作用。
- `Command Frame`：固定时间步下的输入/模拟帧。
- `Prediction`：客户端先行模拟玩家输入。
- `Reconciliation`：服务器结果到达后，客户端对预测结果进行校正。
- `Rollback / Roll Forth`：回滚到服务器确认状态，再重放输入追到当前。
- `Backwards Reconciliation`：服务器为了判定命中，把目标回溯到攻击者开火时刻。
- `ModifyHealthQueue`：延迟处理真实伤害和治疗的队列组件。

## 个人整理版结论

这篇分享最值得学的不是“照抄 Overwatch 的 ECS”，而是它如何用规则约束复杂性。ECS 在这里像胶水，把物理、输入、脚本、网络、技能、命中判定等系统集成起来，同时避免它们互相知道太多。

对于任何需要实时响应、服务器权威和复杂技能组合的游戏，最重要的设计方向是：状态可追踪、行为有边界、副作用可延迟、预测可回滚、系统间少耦合。
