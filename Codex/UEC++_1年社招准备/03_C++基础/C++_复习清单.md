## P0-01 RAII

### 为什么重要
- RAII 是现代 C++ 资源管理的核心，也是智能指针、锁、文件句柄、网络连接等安全管理的基础。
- 游戏客户端代码里经常有资源生命周期问题：对象、句柄、锁、临时缓冲、异步任务。如果没有 RAII 思维，就容易出现泄漏、重复释放、异常路径遗漏释放。

### 核心理解
- RAII 全称是 Resource Acquisition Is Initialization。
- 核心不是“智能指针”本身，而是“资源的获取和释放绑定到对象生命周期”。
- 构造函数获取资源，析构函数释放资源；只要对象离开作用域，析构就会自动执行。
- 它解决的是手动 `new/delete`、`malloc/free`、`lock/unlock` 在多分支、早返回、异常路径下容易忘记释放的问题。

### 最小例子
```cpp
class FScopedFlag
{
public:
    explicit FScopedFlag(bool& InFlag)
        : Flag(InFlag)
    {
        Flag = true;
    }

    ~FScopedFlag()
    {
        Flag = false;
    }

private:
    bool& Flag;
};
```

这个类的意义不是复杂，而是表达一种思想：进入作用域时设置状态，离开作用域时自动恢复状态。

### 常见误区
- 误区：RAII 等于智能指针。
  - 更准确：智能指针是 RAII 的一种典型应用。
- 误区：只有内存需要 RAII。
  - 更准确：锁、文件、句柄、状态恢复、临时注册都可以 RAII。
- 误区：UE 有 GC，所以不用管 RAII。
  - 更准确：UE 的 GC 管 `UObject`，但普通 C++ 资源仍然需要 C++ 生命周期管理。

### 面试表达
- RAII 是把资源生命周期绑定到对象生命周期的 C++ 习惯用法。对象构造时获取资源，析构时释放资源，这样即使函数提前返回或出现异常，也能自动清理资源。智能指针、`std::lock_guard` 都是 RAII 的例子。在 UE 中，`UObject` 的生命周期由 GC 管，但普通 C++ 资源、锁和非 UObject 数据结构仍然需要 RAII 思维。

### 练习题
- 用自己的话解释：为什么 `std::lock_guard` 是 RAII？因为lock_guard会在作用域结束时释放空间，而不会跳过解锁
- 写一个小类，在构造时打印 `Enter`，析构时打印 `Exit`，然后观察不同 `return` 分支是否都会调用析构。都会

## P0-02 智能指针：`unique_ptr`、`shared_ptr`、`weak_ptr`

### 为什么重要
- 智能指针是 C++ 面试高频，也是项目里避免裸指针所有权混乱的重要工具。
- UE C++ 里还要特别区分：`std::shared_ptr`/`TSharedPtr` 不能管理 `UObject` 生命周期。

### 核心理解
- `unique_ptr`：独占所有权，不能拷贝，可以移动。适合“只有一个拥有者”的资源。
- `shared_ptr`：共享所有权，引用计数归零时释放。适合多个普通 C++ 对象共享资源。
- `weak_ptr`：不拥有资源，只观察 `shared_ptr` 管理的对象，用于打破循环引用。
- UE 中：
  - `UObject` 成员引用优先用 `UPROPERTY() TObjectPtr<T>`。
  - 非拥有 UObject 引用可用 `TWeakObjectPtr<T>`。
  - 普通非 UObject C++ 对象可以用 `TUniquePtr`、`TSharedPtr`。

### 最小例子
```cpp
struct FWeaponRuntimeData
{
    int32 Ammo = 30;
};

TUniquePtr<FWeaponRuntimeData> Data = MakeUnique<FWeaponRuntimeData>();
```

这个例子适合非 UObject 的运行时数据。如果 `FWeaponRuntimeData` 改成 `UObject` 派生类，就不该用 `TUniquePtr` 管。

### 常见误区
- 误区：所有指针都换成 `shared_ptr` 就安全。
  - 更准确：`shared_ptr` 会引入共享所有权和引用计数成本，滥用会让生命周期更难判断。
- 误区：`weak_ptr` 可以直接使用对象。
  - 更准确：需要先 `lock()` 或 `Pin()`，确认对象还存在。
- 误区：UE 的 `UObject` 可以用 `shared_ptr`。
  - 更准确：`UObject` 生命周期由 UE GC 管，不能用 `TSharedPtr`/`std::shared_ptr` 管理。

### 面试表达
- 我会先判断对象所有权。如果只有一个所有者，用 `unique_ptr`；如果普通 C++ 对象确实需要共享所有权，用 `shared_ptr`；如果只是观察共享对象，或者要打破循环引用，用 `weak_ptr`。在 UE 中，`UObject` 不走 `shared_ptr` 生命周期，成员引用通常用 `UPROPERTY` 和 `TObjectPtr` 让 GC 识别。

### 练习题
- 为什么双向链表节点如果都用 `shared_ptr` 指向彼此，可能泄漏？因为shared_ptr会互相引用导致双方计数永远有1 无法自动释放内存，正确应该其中一方变成Weak_ptr这样就可以避免相互引用
- UE 中一个 `UActorComponent` 成员引用另一个 `UObject`，你会用 `TSharedPtr` 还是 `UPROPERTY() TObjectPtr`？为什么？`UPROPERTY() TObjectPtr`，TSharedPtr是对普通C++对象使用的

## P0-03 拷贝构造、移动构造、赋值运算符

### 为什么重要
- 这是 C++ 面试最常见的对象生命周期题。
- 如果你写资源管理类、容器元素、运行时数据结构，必须知道拷贝和移动会发生什么。

### 核心理解
- 拷贝构造：用已有对象创建新对象，资源通常需要复制。
- 拷贝赋值：两个已存在对象之间赋值，需要处理旧资源、自赋值、深拷贝。
- 移动构造：用即将不用的对象创建新对象，资源所有权转移，减少深拷贝成本。
- 移动赋值：两个已存在对象之间转移资源。
- Rule of 3：如果你手写析构、拷贝构造、拷贝赋值中的一个，通常要考虑另外两个。
- Rule of 5：C++11 后还要考虑移动构造和移动赋值。
- Rule of 0：如果能用标准库对象管理资源，就尽量不手写这些特殊函数。

### 最小例子
```cpp
class FBuffer
{
public:
    explicit FBuffer(int32 InSize)
        : Size(InSize), Data(new int32[InSize])
    {
    }

    ~FBuffer()
    {
        delete[] Data;
    }

private:
    int32 Size = 0;
    int32* Data = nullptr;
};
```

这个类如果不手写拷贝构造和赋值，默认拷贝会复制裸指针，两个对象析构时会重复 `delete[]`。这就是为什么资源类要关注 Rule of 3/5。

### 常见误区
- 误区：拷贝构造就是赋值运算符。
  - 拷贝构造是创建新对象，赋值运算符是已有对象改值。
- 误区：移动后对象不能析构。
  - 移动后对象仍然有效，但内容通常不应依赖；它必须能安全析构。
- 误区：移动语义只和性能有关。
  - 它还表达资源所有权转移。

### 面试表达
- 拷贝语义是复制对象状态，移动语义是转移资源所有权，常用于避免昂贵深拷贝。写资源管理类时，如果自己管理裸资源，就要考虑析构、拷贝构造、拷贝赋值、移动构造、移动赋值。更好的方式是遵循 Rule of 0，用标准库或 UE 容器管理资源，减少手写生命周期代码。

### 练习题
- 一个类里有裸指针成员，默认拷贝构造可能导致什么问题？
- 移动构造后，源对象应该处于什么状态？

## P0-04 虚函数、虚表、多态、虚析构

### 为什么重要
- UE 和游戏客户端大量使用继承、多态、接口和虚函数。
- 面试会追问虚函数实现、虚析构、构造函数中调用虚函数等问题。

### 核心理解
- 多态：用基类指针或引用调用虚函数，运行时根据真实对象类型分派到子类实现。
- 虚表：编译器实现动态派发的一种常见机制，每个含虚函数的类通常有虚表，对象里有指向虚表的指针。
- 虚析构：如果可能通过基类指针删除派生类对象，基类析构函数必须是 virtual。
- 纯虚函数：`= 0`，用于定义抽象接口。

### 最小例子
```cpp
class FWeapon
{
public:
    virtual ~FWeapon() = default;
    virtual void Fire() = 0;
};

class FRifle : public FWeapon
{
public:
    virtual void Fire() override
    {
        // Rifle fire logic
    }
};
```

### 常见误区
- 误区：所有函数都应该 virtual。
  - virtual 有设计含义和一点运行时成本，不需要扩展的函数不应随便 virtual。
- 误区：构造函数可以是虚函数。
  - 构造函数不能是虚函数。
- 误区：析构函数不需要 virtual。
  - 如果基类用于多态删除，析构必须 virtual。

### 面试表达
- C++ 多态通常通过虚函数实现，调用方持有基类指针或引用，实际调用哪个函数由对象真实类型决定。虚表是常见实现机制。只要类作为多态基类使用，就应该提供虚析构，避免通过基类指针删除派生对象时只调用基类析构。

### 练习题
- 为什么有虚函数的接口类通常要写 `virtual ~Base() = default;`？
- 构造函数中调用虚函数会发生什么？为什么不推荐？

## P0-05 对象切片

### 为什么重要
- 你答卷里明确提到没听过对象切片，这是 C++ 多态面试常见追问。
- 对象切片能暴露你是否真正理解“按值传递”和“多态必须通过指针/引用”。

### 核心理解
- 对象切片发生在：把派生类对象按值赋给基类对象。
- 派生类多出来的成员会被切掉，只保留基类那部分。
- 这样会失去多态行为，因为对象本身已经变成基类对象。

### 最小例子
```cpp
class FAnimal
{
public:
    virtual FString Speak() const { return TEXT("Animal"); }
};

class FDog : public FAnimal
{
public:
    virtual FString Speak() const override { return TEXT("Dog"); }
};

void PrintAnimal(FAnimal Animal) // 按值传递，会切片
{
    Animal.Speak();
}
```

应该改成：
```cpp
void PrintAnimal(const FAnimal& Animal)
{
    Animal.Speak();
}
```

### 常见误区
- 误区：只要函数是 virtual，就不会切片。
  - 如果已经按值拷贝成基类对象，真实类型就丢了。
- 误区：切片是崩溃问题。
  - 它通常不崩溃，而是逻辑悄悄错。

### 面试表达
- 对象切片是派生类对象按值赋给基类对象时，派生类部分被丢弃，只保留基类子对象。要避免切片，多态对象应通过指针或引用传递，比如 `const Base&` 或 `Base*`。

### 练习题
- 写一个会发生对象切片的函数签名，再写出修正版本。
- 为什么 `TArray<Base>` 存派生类对象会有问题？应该怎么设计？

## P0-06 STL/UE 容器：数组、哈希表、集合

### 为什么重要
- 游戏逻辑大量使用容器：角色列表、技能表、Buff 列表、任务状态、对象缓存。
- 面试会追问容器选择、复杂度、迭代器失效、哈希冲突。

### 核心理解
- `std::vector`/`TArray`：连续内存，随机访问快，尾部插入快，中间插入删除慢。
- `std::map`：有序树结构，查找/插入/删除通常 O(log n)。
- `std::unordered_map`/`TMap`：哈希表，平均 O(1)，最坏可能退化。
- `std::set`/`TSet`：集合，适合去重和快速判断是否存在。

### 常见误区
- 误区：哈希表永远 O(1)。
  - 平均 O(1)，哈希冲突严重或 rehash 时会变慢。
- 误区：`TArray` 删除元素不会影响引用。
  - 删除、扩容、移动元素都可能让引用、指针、索引语义失效。
- 误区：容器越高级越好。
  - 小数据量时简单数组可能更快、更好维护。

### 面试表达
- 我会根据访问模式选容器。如果需要连续遍历和按索引访问，优先 `TArray`；如果要按 Key 找数据，用 `TMap`；如果只关心是否存在和去重，用 `TSet`。我也会注意扩容和删除导致的引用/迭代器失效，以及哈希表冲突和 rehash 成本。

### 练习题
- 为什么遍历 `TArray` 时删除元素要格外小心？
- 技能表按 `SkillID` 查找，你会用 `TArray` 还是 `TMap`？为什么？

## P0-07 迭代器失效、引用失效、哈希冲突

### 为什么重要
- 这些问题在游戏运行时很容易变成偶现 bug。
- 面试喜欢问“为什么这段代码偶尔崩”。

### 核心理解
- `vector/TArray` 扩容会搬迁内存，旧指针/引用/迭代器可能全部失效。
- 删除元素会导致后续元素移动，索引和引用可能不再指向原对象。
- 哈希冲突是多个 Key 映射到同一个桶，需要冲突处理。
- 哈希表 rehash 会重建桶，迭代器也可能失效。

### 常见误区
- 误区：我只是保存了一个元素引用，容器扩容和我没关系。
  - 扩容会改变底层内存。
- 误区：哈希冲突是错误。
  - 冲突是正常现象，关键是冲突处理和哈希质量。

### 面试表达
- 连续数组容器扩容时可能重新分配内存，所以之前保存的元素指针、引用、迭代器会失效。删除元素也可能移动后续元素。哈希表平均查找很快，但存在哈希冲突和 rehash，不能认为永远 O(1)。

### 练习题
- 如果你需要在遍历 `TArray` 时删除多个元素，你会怎么写？
- 为什么保存 `TArray` 元素指针到别处可能危险？

## P0-08 线程安全、锁、原子、竞态条件

### 为什么重要
- UE 大部分 Gameplay 在 GameThread，但异步加载、任务系统、网络、资源处理都可能涉及多线程。
- 面试会问基础并发概念，至少要能说清楚风险。

### 核心理解
- 竞态条件：结果依赖多个线程执行时序。
- 数据竞争：多个线程同时访问同一内存，至少一个写，且没有同步。
- 锁：保护临界区，保证同一时间只有一个线程访问共享数据。
- 原子：对简单数据提供不可分割操作，适合计数、状态标记等。
- 死锁：多个线程互相等待对方持有的锁。

### 最小例子
```cpp
std::mutex Mutex;
int32 Counter = 0;

void Add()
{
    std::lock_guard<std::mutex> Lock(Mutex);
    ++Counter;
}
```

### 常见误区
- 误区：加锁就一定安全。
  - 锁粒度、锁顺序、死锁、性能都要考虑。
- 误区：原子可以替代所有锁。
  - 原子适合简单操作，复杂不变量仍需要锁或更高层同步。
- 误区：UE Gameplay 随便开线程改 Actor。
  - 大多数 Actor/UObject 操作应在 GameThread。

### 面试表达
- 线程安全问题的核心是共享状态。如果多个线程读写同一数据，就需要同步。简单计数可以用原子，复杂数据结构通常用锁保护临界区。在 UE 中还要注意大部分 `UObject` 和 Actor 操作不能随意放到后台线程执行，通常需要回到 GameThread。

### 练习题
- 什么是数据竞争？和竞态条件有什么区别？
- 为什么后台线程直接修改 Actor 状态可能有风险？

## P1-09 C++ 内存布局：栈、堆、静态区、生命周期

### 为什么重要
- 这是基础题，但也是判断你 C++ 是否扎实的入口。
- 你答卷里对静态区和更细生命周期还不稳。

### 核心理解
- 栈：自动存储期，函数调用结束后自动销毁局部对象。
- 堆：动态分配，需要所有权管理，现代 C++ 应尽量交给 RAII/智能指针。
- 静态存储区：全局变量、静态变量，程序启动到结束期间存在。
- 临时对象：表达式过程中产生，生命周期受语境影响。

### 常见误区
- 误区：栈对象一定更安全。
  - 返回局部变量引用仍然危险。
- 误区：堆对象一定要手动 delete。
  - 应优先让智能指针或容器管理。

### 面试表达
- 我会从存储期解释对象生命周期：局部对象通常在栈上自动销毁，动态分配对象在堆上，需要明确所有权，静态对象贯穿程序生命周期。现代 C++ 尽量用 RAII 和容器管理资源，减少手动释放。

### 练习题
- 为什么不能返回局部变量的引用？
- 静态局部变量什么时候初始化，生命周期到什么时候？

## P1-10 模板、重载、类型推导

### 为什么重要
- 模板和类型推导是 C++ 常见编译错误来源。
- UE 里 `Cast<T>`、`NewObject<T>`、`TArray<T>`、`TSubclassOf<T>` 都离不开模板。

### 核心理解
- 模板是编译期代码生成机制，不是运行时多态。
- 函数重载根据参数列表选择函数。
- `auto` 会丢掉部分引用和 cv 限定，除非写 `auto&`、`const auto&`。
- 模板错误通常很长，要从第一处自己代码相关错误看起。

### 常见误区
- 误区：模板参数是运行时传入。
  - 模板实例化发生在编译期。
- 误区：`auto` 总是推导成你想要的类型。
  - 引用、const、数组退化都要注意。

### 面试表达
- 模板提供编译期泛型能力，编译器会根据使用场景实例化具体类型。函数重载是同名函数按参数差异选择。使用 `auto` 时我会注意引用和 const 是否被保留，必要时显式写 `const auto&`。

### 练习题
- `auto X = SomeVector[0];` 和 `auto& X = SomeVector[0];` 有什么区别？

## P1-11 编译错误、链接错误、头文件依赖

### 为什么重要
- UE C++ 编译链更复杂，有 C++ 编译器、UHT、UBT、模块依赖。
- 能定位编译错误是工程能力。

### 核心理解
- 编译错误：单个源文件编译阶段出错，如类型未定义、语法错误。
- 链接错误：编译过了，但符号找不到，如缺少模块依赖或函数声明了没实现。
- UHT 错误：反射宏、`generated.h`、类型暴露等问题。
- 头文件依赖：能前向声明就前向声明，必须知道完整定义时再 include。

### 常见误区
- 误区：看到一长串模板错误就从最后一行看。
  - 通常要找第一处和自己代码相关的位置。
- 误区：include 了头文件就不需要 Build.cs 依赖。
  - UE 模块还需要在 Build.cs 加依赖。

### 面试表达
- 我会先区分是 UHT、编译还是链接阶段错误。UHT 错误通常和反射宏、`.generated.h`、暴露类型有关；链接错误常见于函数未实现或模块依赖没加；普通编译错误则看 include、前向声明、类型定义和模板实例化位置。

### 练习题
- UE 中 include 正确但仍然链接失败，可能是什么原因？
- `.generated.h` 没放最后可能导致什么问题？

## P1-12 复杂度与常见算法恢复

### 为什么重要
- 你算法半年没练，不需要走竞赛路线，但要避免基础算法拖后腿。
- 游戏客户端社招也会问基础数据结构和复杂度。

### 核心理解
- 时间复杂度描述输入规模增长时操作次数增长趋势。
- 空间复杂度描述额外内存使用趋势。
- 常见面试算法：数组、字符串、哈希、双指针、二分、栈队列、树、DFS/BFS。

### 复习顺序
- 第 1 阶段：数组、字符串、哈希、双指针。
- 第 2 阶段：栈、队列、二分、链表。
- 第 3 阶段：树、DFS/BFS。
- 第 4 阶段：动态规划入门。

### 面试表达
- 面对算法题我会先明确输入规模和目标复杂度，再选择数据结构。比如需要快速查找就考虑哈希，需要有序边界就考虑二分，需要层级遍历就考虑 BFS。

### 练习题
- 为什么二分查找容易写错边界？你习惯用哪种区间写法？
- `unordered_map` 查找平均 O(1)，为什么最坏不是 O(1)？

### 面试表达

## P2-14 C++ 与 UE C++ 的边界

### 为什么重要
- UE C++ 不是纯 C++，但也不是完全不同的语言。
- 面试时能说清“哪些走 C++，哪些走 UE 对象系统”是加分项。

### 核心理解
- 普通算法、非 UObject 数据结构、资源管理仍然遵守 C++ 规则。
- `UObject` 生命周期、反射、序列化、复制、蓝图暴露走 UE 系统。
- `USTRUCT` 是值类型，不是 UObject，没有 GC 生命周期。
- `TSharedPtr` 管普通 C++ 对象，不管 UObject。

### 面试表达
- 我会区分普通 C++ 对象和 UE 反射对象。普通运行时数据可以用 C++ RAII 和智能指针管理；需要编辑器、蓝图、GC、复制支持的对象则接入 UE 的 `UObject`/`UPROPERTY` 系统。

### 练习题
- 一个技能配置数据应该用 `USTRUCT`、`UDataAsset` 还是普通 C++ struct？分别适合什么场景？
- 为什么 `UObject` 不适合用 `shared_ptr` 管理？
