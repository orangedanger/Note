## A 组：反射、蓝图暴露、UHT、复制

### 评分

- 理由：大部分方向正确，能答出核心区别；个别题需要精确到 UHT/反射术语和网络复制触发条件。

### 已经比较稳的点
- `BlueprintCallable` 有执行引脚，`BlueprintPure` 无执行引脚，这个答对。
- `BlueprintType` 用于蓝图变量/参数类型，`Blueprintable` 用于蓝图继承，答对。
- `GetHealthPercent()` 更适合 `BlueprintPure`，`ApplyDamage()` 不适合 Pure，方向对。
- `UFUNCTION()` 不加 `BlueprintCallable` 也可以被 `AddDynamic` 绑定，答对。
- 客户端本地改 replicated 属性通常不会同步给服务器，答对。

### 需要修正的点
- `.generated.h` 不是“引用那个 .gen 文件”。UE 生成的是 `.generated.h`，它会被当前头文件 include，用来注入 UHT 生成的反射声明和胶水代码。
- `GENERATED_BODY()` 是类体里的宏展开入口，会把 UHT 需要的声明挂进类里；`.generated.h` 是头文件末尾 include 的生成文件，两者配套工作。
- `UPROPERTY(EditAnywhere)` 不改变 GC 行为，这个结论对；但更准确是：`UPROPERTY` 让属性进入属性系统，GC 只关心其中的 UObject 引用。
- `UPROPERTY()` 对 `float` 的意义不是“属性复制”本身。复制还需要 `Replicated` 和 `GetLifetimeReplicatedProps`。对 `float`，空 `UPROPERTY()` 主要让它进入反射/序列化等属性系统；对 `TObjectPtr<UObject>`，还会让 GC 看到引用链。
- `ReplicatedUsing` 绑定的 OnRep 函数通常在客户端收到服务器复制来的新值时调用，不是服务器本地一改值就立刻调用。
- `UPROPERTY(TMap<int32, UObject*>)` 这题你误解成“UPROPERTY 里不能填 TMap”。真正的问题是 `UPROPERTY(...)` 括号里写的是 specifier，不是变量类型。类型要写在下一行或同一声明中。

### 建议改写
```cpp
// 正确的属性声明形态
UPROPERTY()
TMap<int32, TObjectPtr<UObject>> ObjectMap;
```

面试表达：
`UPROPERTY()` 的括号里写的是属性 specifier，例如 `EditAnywhere`、`BlueprintReadWrite`、`Replicated`。变量类型写在宏后面的 C++ 声明里。遇到 UHT 报错时，我会先检查 UPROPERTY 语法、容器类型是否被反射支持，以及 UObject 引用是否需要使用 `TObjectPtr`。

### 需要你回头修的题
- `.generated.h` 和 `GENERATED_BODY()` 分别解决什么问题？前者让这个类引入了UHT生成的胶水代码和反射声明
- `UPROPERTY()` 对 `float` 和对 `TObjectPtr<UObject>` 的意义有什么不同？对于float而言它提供序列化和反射等，对于后者他还让GC能看到引用链
- `Replicated` 和 `ReplicatedUsing` 的区别是什么？当变量在服务器权威上发送变化时都会把变化后的结果发送给客户端，后者会在客户端调用绑定的OnRep函数

## B 组：GC、UObject 引用、指针语义

### 评分
- 当前：`2.5/4`
- 理由：你已经知道 `UPROPERTY() TObjectPtr` 比单独 `TObjectPtr` 更安全，也知道 `TSharedPtr` 不适合 UObject；但 GC、Outer、Root、局部裸指针的细节还需要校准。

### 已经比较稳的点
- `TSharedPtr<UMyObject>` 是错误方向，因为 UObject 生命周期由 UE GC 管，不由共享引用计数管。
- `FVector` 不是 UObject，不需要 GC 管理，方向对。
- 蓝图子类默认值覆盖 C++ 父类默认值这个方向对，要补成“蓝图生成类自己的 CDO 默认值”。
- `AddToRoot` 日常使用会导致对象不回收，这个风险判断对。

### 需要修正的点
- `UPROPERTY() TObjectPtr<UObject>` 和单独 `TObjectPtr<UObject>` 的区别，不是“前者不会突然 GC”这么简单。更准确是：前者作为反射属性能被 GC 引用收集器看到，后者只是一个 UObject 指针包装，未必进入反射引用链。
- `UPROPERTY()` 不是只在 `.h` 里“对不想回收的变量使用”。它是 UE 属性系统入口；GC 只是它对 UObject 引用的一个重要作用。
- 局部变量 `UObject* Obj = NewObject<UMyObject>()` 在一次同步函数里通常没问题，不是因为“出了作用域就被回收”。更准确是：你只在当前调用栈临时使用它，不跨帧、不存长期引用，风险较低；但如果存成成员且 GC 不可见，后续 GC 后就可能悬空。
- `Outer` 合理不等于一定不会 GC。Outer 表示对象归属、路径和上下文，不是万能强引用。对象要长期存活，仍然需要 Root、可达引用链、注册到引擎体系，或被 `UPROPERTY`/`AddReferencedObjects` 上报。

### 三个机制的区别
- `UPROPERTY()`：最常见方案。UObject 成员引用进入反射系统，让 GC 可追踪。
- `AddToRoot()`：把对象强行加入 Root 集合，适合少数全局/特殊生命周期对象；需要手动 `RemoveFromRoot()`，不适合日常默认用。
- `FGCObject::AddReferencedObjects()`：普通非 UObject C++ 管理类持有 UObject 引用时，用它手动向 GC 上报引用。

### 建议改写
`Outer` 决定 UObject 的归属和命名路径，也常用于表达生命周期上下文，但它不是替代 `UPROPERTY` 的强引用方案。一个对象是否会被 GC，关键看它是否能从 Root 通过可追踪引用链到达。长期成员引用应使用 `UPROPERTY() TObjectPtr<T>`，非 UObject 管理者则需要 `FGCObject` 等方式上报。

### 需要你回头修的题
- `UPROPERTY()`、`AddToRoot()`、`FGCObject::AddReferencedObjects()` 分别适合解决什么场景？第一个让是成员变量能引入反射系统，被GC识别引用链，第二个是为一些相对独立的全局对象加入Root，需要RemoveFromRoot进行手动管理，最后一个是对于非UObject对象持有Object对象需要手动进行上报GC
- 为什么局部变量 `UObject* Obj = NewObject<UMyObject>();` 在一次函数调用里通常没问题，但把 `Obj` 存成无 `UPROPERTY` 成员就有风险？因为前者是短时的，不会跨帧，长时间持有的对象，但如果需要存成成员对象，那么他就会长时间持有，如果补通过UPROPERTY将对象引入反射系统，那么这个对象就不会被GC在调用链中看到，导致对象可能变成悬挂指针。
- `Outer` 合理是否等于一定不会被 GC？为什么？不等于，如果Outer长期持有，但没有通过UPROPERTY() TObject<T> obj;对象引用那么这个Outer很可能就会被GC

## C 组：对象创建、组件注册、生命周期

### 评分
- 当前：`2.5/4`
- 理由：你能说出注册、附加、`PostInitializeComponents`、`CollisionHandlingOverride` 等关键词，但构造函数、`OnConstruction`、`BeginPlay` 的边界还需要重新对齐。

### 已经比较稳的点
- `NewObject<UStaticMeshComponent>(this)` 后还需要注册和附加，答对。
- 已注册到 World 的组件运行时更常用 `AttachToComponent`，答对。
- 碰撞导致 Spawn 失败时检查 `CollisionHandlingOverride`，答对。
- 只依赖自己组件初始化完成、不依赖其他 Actor 的逻辑，放 `PostInitializeComponents` 更合适，答对。
- 依赖 PlayerController/Pawn possession 时，`BeginPlay` 不一定够，这个判断很好。

### 需要修正的点
- `OnConstruction` 不适合“创建默认子对象”。默认子对象应在 C++ 构造函数里创建。`OnConstruction`/Construction Script 更适合根据编辑器参数或生成参数调整实例状态、生成预览、摆放组件等。
- 组件没注册，不是不可以附加到 Actor；未注册组件可以先 `SetupAttachment` 记录关系。问题是它没有进入 World，所以不会创建渲染/物理状态，Tick/碰撞/可见表现也可能没有。
- `SetupAttachment` 的“为什么”是：它设置未注册组件将来注册时的附加父子关系；`AttachToComponent` 是运行时附加，带 `FAttachmentTransformRules`，适合已注册组件。
- `SpawnActorDeferred` 不是“构造函数里 Spawn”。它是先 Spawn 出 Actor 但延迟 Construction Script/最终初始化，让你在 `FinishSpawning` 前设置属性。构造函数里 Spawn 是指在某个 Actor 的 C++ constructor 里调用 `GetWorld()->SpawnActor`，这是不推荐的。
- `SpawnActor` 和 `NewObject` 的最大区别不是只在于 Transform，而是 Actor 是否进入 World 并走完整 Actor 生命周期。
- Subsystem 不是两个场景 Actor 互相引用时“最安全”的默认答案。它能解耦，但也可能过度设计。编辑器引用显式稳定但耦合强；Tag 查找灵活但易脆；Subsystem/注册表适合全局服务或动态发现。
