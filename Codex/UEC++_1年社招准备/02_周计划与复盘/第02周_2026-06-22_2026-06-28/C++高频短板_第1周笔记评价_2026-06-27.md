## 1. `std::lock_guard` 为什么能避免忘记解锁

你的回答：
> 因为它是RAII的用法，在构造时进行加锁，析构时会进行解锁，当 上的锁离开了作用域，这个锁就会被析构，就会解锁

### 评分
- 当前：`3.5/4`
- 理由：核心完全对，只是表达有一点口语和错字。

### 哪里对
- 能说出 `std::lock_guard` 是 RAII。
- 能说出构造加锁、析构解锁。
- 能说出离开作用域自动析构。

### 需要修正
- 不要说“上的锁”，改成“栈上的 `lock_guard` 对象”。
- 可以补一句：异常或提前 `return` 时也会自动解锁。

### 建议改写
`std::lock_guard` 使用 RAII 管理互斥锁。它在构造时加锁，在析构时自动解锁，所以只要 `lock_guard` 是栈对象，离开作用域时就会自动释放锁。这样即使函数提前 `return` 或抛异常，也不容易忘记解锁。

## 2. 为什么 `UObject` 成员不应该用 `std::shared_ptr` 管生命周期

你的回答：
> 因为UObject成员的声明周期由UE的GC进行管理，如果用shared_ptr，尽管仍然有计数但因为GC的root集被标记PendingKill那么不管shared_ptr是否有计数这个UObject对象都会被回收

### 评分
- 当前：`3/4`
- 理由：方向对，知道 `UObject` 由 GC 管，`shared_ptr` 计数救不了它。但“Root 集被标记 PendingKill”这个说法不准确。

### 哪里对
- 知道 `UObject` 生命周期由 UE GC 管理。
- 知道 `std::shared_ptr` 的引用计数不能阻止 GC 回收 `UObject`。

### 需要修正
- GC 不是因为“Root 集被标记 PendingKill”而回收对象。
- 更准确是：GC 从 Root Set 出发，沿着 `UPROPERTY` 等可追踪引用做可达性标记；如果某个 `UObject` 不可达，就可能被回收。
- `std::shared_ptr<UObject>` 的引用计数对 UE GC 不可见，所以 GC 不会因为它而认为对象还活着。

### 建议改写
`UObject` 的生命周期由 UE GC 管理。GC 会从 Root Set 出发，沿着 `UPROPERTY`、`TObjectPtr` 等可追踪引用判断对象是否可达。`std::shared_ptr` 的引用计数对 GC 不可见，所以即使 `shared_ptr` 还有计数，如果这个 `UObject` 没有被 GC 可见的引用持有，仍然可能被回收并留下悬空指针。因此 `UObject` 成员通常用 `UPROPERTY() TObjectPtr<T>`，普通 C++ 对象才用 `shared_ptr`。

## 3. `std::move` 为什么不等于立刻移动资源

你的回答：
> std::move只是将表达式强行转为为右值引用，需要移动构造或移动赋值去实现移动资源

### 评分
- 当前：`3.5/4`
- 理由：这题答得很好，已经接近可面试表达。

### 哪里对
- 知道 `std::move` 是转换。
- 知道真正移动资源的是移动构造或移动赋值。

### 需要补充
- `std::move` 只是让移动操作有机会被匹配，不保证一定发生移动。
- 如果对象是 `const`，或类型没有可用移动构造，可能走拷贝或直接无法调用。

### 建议改写
`std::move` 本身不移动资源，它只是把表达式转换成右值引用，让编译器有机会匹配移动构造或移动赋值。真正转移资源的是类型自己的移动构造函数或移动赋值运算符。如果类型没有可用移动操作，`std::move` 并不会自动帮它移动。

## 4. 移动构造里为什么通常要把源对象指针置空

你的回答：
> 因为源对象仍然需要进行正常的析构如果源对象指针不置为空则会导致，析构时源对象指针仍然指向移动后的对象从而进行内存的释放导致移动后的对象部分参数被释放

### 评分
- 当前：`3.25/4`
- 理由：方向对，知道源对象还会析构，也知道不置空会出资源释放问题。表达上还需要换成更准确的“同一资源被两个对象拥有”。

### 哪里对
- 知道移动后源对象仍会析构。
- 知道源对象指针不处理会导致释放风险。

### 需要修正
- 不是“源对象指针指向移动后的对象”，而是“源对象和目标对象的指针都指向同一份资源”。
- 风险不只是“移动后的对象部分参数被释放”，更准确是 double delete、悬空指针、use-after-free。

### 建议改写
移动构造把资源指针从源对象转交给目标对象后，源对象仍然会析构。如果不把源对象的指针置为 `nullptr`，源对象和目标对象就会同时指向同一份资源，两个对象析构时可能重复释放同一块内存，造成 double delete 或悬空指针。所以移动后要把源对象调整到安全可析构状态。

## 5. 为什么 `TArray<Base>` 存派生类对象会有切片风险

你的回答：
> 因为这里存储方式是按值存储，导致如果存储派生类对象会使得派生类新增变量不会被存储且多态不会生效

### 评分
- 当前：`3.5/4`
- 理由：核心答对了，已经能说出按值存储、派生类新增变量丢失、多态不生效。

### 哪里对
- 知道 `TArray<Base>` 是按值存储 `Base` 对象。
- 知道派生类部分会被切掉。
- 知道多态会失效。

### 需要补充
- 如果是普通 C++ 多态类，应该用 `TArray<TUniquePtr<Base>>`、`TArray<TSharedPtr<Base>>` 或其他间接存储方式。
- 如果是 UE 的 `UObject`/`AActor`，不要按值存，通常用 `TArray<TObjectPtr<UBase>>`、`TArray<TWeakObjectPtr<AActor>>` 或 `TArray<AActor*>` 这类指针/引用语义。

### 建议改写
`TArray<Base>` 是按值保存 `Base` 对象。如果把 `Derived` 放进去，只会拷贝出其中的 `Base` 子对象，派生类新增数据和动态类型都会丢失，虚函数多态也会失效。普通 C++ 多态对象应使用指针或智能指针容器；UE 的 `UObject`/`AActor` 则通常用 `TObjectPtr`、`TWeakObjectPtr` 或原始指针参数引用。

## 6. `const Base&` 为什么能避免对象切片

你的回答：
> 因为他传递的是地址，而不是单纯的值，地址还是派生类开辟的地址，所有一些派生类新增的变量和多态能正常使用

### 评分
- 当前：`3/4`
- 理由：方向对，知道不是按值拷贝，也知道多态可以保留。但“引用就是地址”的说法不够严谨。

### 哪里对
- 知道 `const Base&` 不会创建新的 `Base` 值对象。
- 知道引用仍然绑定到原来的派生类对象。
- 知道虚函数多态可以正常发生。

### 需要修正
- 面试里不要直接说“引用传的是地址”。引用可以理解为别名，关键点是“不发生按值拷贝”。
- 更准确是：`const Base&` 绑定到原始对象的基类子对象，但对象的动态类型仍然是 `Derived`。

### 建议改写
`const Base&` 避免切片，是因为它不会创建一个新的 `Base` 值对象，而是引用原来的对象。即使参数类型是 `Base&`，它仍然可以绑定到 `Derived` 对象的基类部分，对象的动态类型没有丢失，所以调用虚函数时仍然能派发到派生类实现。

## 7. 为什么问题是派生类析构没被调用，不是基类析构没被调用

你的回答：
> 因为你用的是基类指针指向派生类对象，这是你的基类指针对象要被销毁，且析构不是多态，那么就不会调用派生类的析构函数，只能找到基类的析构函数

### 评分
- 当前：`3.5/4`
- 理由：这题已经明显修正过来了，核心是对的。

### 哪里对
- 知道场景是 `Base*` 指向 `Derived`。
- 知道非虚析构不会动态派发到派生类析构。
- 知道结果是只调用基类析构。

### 需要修正
- 不要说“基类指针对象要被销毁”，更准确是“通过基类指针删除它所指向的对象”。
- 可以补充：标准层面这是未定义行为风险，不只是简单的资源泄漏。

### 建议改写
因为 `delete BasePtr` 删除的是 `BasePtr` 指向的那个 `Derived` 对象。如果 `Base` 的析构函数不是 `virtual`，析构不会按动态类型派发，可能只调用 `Base::~Base()`，不调用 `Derived::~Derived()`。所以问题在于派生类自己的析构逻辑没有执行，而不是基类析构没执行。

## 8. 有虚函数但永远不会通过基类指针删除对象，是否一定要虚析构

你的回答：
> 可以不用虚析构，但这样使用不能确保不会用基类指针删除对象，最好写成virtual ~ABase() = default;的格式

### 评分
- 当前：`3.25/4`
- 理由：判断方向对，知道理论上可以不写，也知道工程上多态基类通常建议写虚析构。

### 哪里对
- 知道是否需要虚析构和“会不会通过基类指针删除”有关。
- 知道为了接口安全，通常写 `virtual ~Base() = default;`。

### 需要补充
- 如果设计上明确禁止通过基类指针删除，也可以把基类析构写成 `protected` 且非虚，用类型系统阻止外部 `delete Base*`。
- 但面试初级表达不需要展开太深，先说“多态基类通常写虚析构”最稳。

### 建议改写
如果能严格保证不会通过基类指针删除对象，理论上可以不写虚析构。但在工程实践里，只要一个类作为多态基类或接口类使用，通常就写 `virtual ~Base() = default;`，这样以后即使有人通过 `Base*` 删除派生类对象，也能正确先调用派生类析构，再调用基类析构。
