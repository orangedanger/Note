你的回答：

### 哪里对
- 你知道 `TObjectPtr` 主要用于 UE 对象引用。
- 你知道裸指针可以用于函数参数、局部临时访问。
- 你知道 `TWeakObjectPtr` 不负责保持对象存活。
- 你知道 `TSharedPtr` 是引用计数，并且循环引用要用 `TWeakPtr` 打断。

### 需要修正
- `TObjectPtr` 本身不是“让对象不被 GC”的完整答案。常见成员写法应该是 `UPROPERTY() TObjectPtr<UObjectType> Ptr;`，重点是这个成员进入 UE 反射/引用追踪系统。
- 裸 `UObject*` 不是只能在 `.cpp` 用，函数参数、局部变量、临时缓存都可以用；危险主要发生在“成员长期保存但 GC 不可见”。
- `TWeakObjectPtr` 不是“中间变量”专用，它适合长期保存一个非持有观察引用，例如缓存一个目标 Actor，但不希望阻止它销毁。
- `TSharedPtr`/`TWeakPtr` 不要用于 `UObject` 派生对象；它们适合 `FMyData`、工具类、Slate 数据模型等普通 C++ 对象。
- 拼写注意：`TObjectPtr`、`TWeakObjectPtr`。

### 四条规则修正版
1. `UPROPERTY() TObjectPtr<UMyObject>`：用于 UObject 派生成员引用，让 UE 反射/GC 能看到这条引用链，适合 Actor/Component/UObject 的长期成员引用。  
2. `UObject*` 裸指针：适合函数参数、局部变量、立即使用的临时引用；不适合在 UObject 成员里长期保存而不加 `UPROPERTY`。  
3. `TWeakObjectPtr<AActor>`：用于观察 UObject/Actor，不拥有对象、不阻止 GC 或销毁；每次使用前用 `IsValid()` 检查。  
4. `TSharedPtr<FMyData>` / `TWeakPtr<FMyData>`：用于非 UObject 的普通 C++ 对象；不要用它们管理 `UObject`，因为 UE 对象生命周期由 GC/Outer/World 管理。  

### 更好的面试表达
UE 里要先区分 UObject 和普通 C++ 对象。UObject 派生对象的生命周期主要由 UE 的对象系统和 GC 管理，成员引用通常写成 `UPROPERTY() TObjectPtr<T>`，这样反射系统和 GC 能追踪引用链。裸 `UObject*` 可以用于参数和局部临时访问，但如果作为长期成员保存且没有 `UPROPERTY`，GC 可能不知道这条引用。`TWeakObjectPtr` 用来保存非拥有观察引用，对象销毁后可以通过 `IsValid()` 判断。`TSharedPtr`、`TWeakPtr` 是普通 C++ 引用计数工具，适合非 UObject 类型，不应该拿来管理 UObject。

## 13. 裸 `UObject*` 成员为什么危险

你的回答：
> 好像没那么危险，不过TObjectPtr是Ue自己做了适配专门去包装裸指针的为了更精准的GC

### 评分
- 当前：`1.5/4`
- 理由：这里还没有抓住面试题真正考点。裸指针不是天然错误，但“裸 `UObject*` 成员不被 GC 引用链追踪”是核心风险。

### 哪里对
- 你没有把裸指针一棍子打死，这是对的。UE 里函数参数和局部变量大量使用裸指针。
- 你知道 `TObjectPtr` 是 UE 对 UObject 指针做的适配。

### 需要修正
- 危险的不是“裸指针”这三个字，而是“长期成员引用 + GC 不可见 + 对象可能被回收或销毁”。
- `TObjectPtr` 的价值不只是“更精准”，还包括 UE5 的对象句柄、编辑器懒加载、Cook 依赖跟踪，以及和 GC 引用收集接口配合。
- 如果成员没有 `UPROPERTY`，即使它是 `TObjectPtr`，也不等于自动成为反射属性。面试时要把 `UPROPERTY` 放进答案。

### 标准回答
裸 `UObject*` 作为函数参数或局部变量并不一定危险，危险的是把它作为成员长期保存但没有 `UPROPERTY` 或其他 GC 引用上报机制。UE GC 是从 Root 和可追踪引用链出发标记对象，如果某个 UObject 只被一个普通 C++ 成员裸指针指着，GC 可能看不到这条引用并把对象回收。回收后这个裸指针不会自动变成安全空值，继续访问就可能变成悬空指针。UE5 推荐成员引用写成 `UPROPERTY() TObjectPtr<T>`，让引用进入反射/GC 系统；如果只是观察不持有对象，则使用 `TWeakObjectPtr<T>` 并在使用前检查 `IsValid()`。

- 销毁阶段一般表达为 `Destroy()` 触发销毁流程，Gameplay 结束通知是 `EndPlay`，随后有 `Destroyed` 等销毁相关回调；面试里不要简单说 `Destroyed -> EndPlay`，容易被追问。

### 简化顺序修正版
适合面试的简化版本：

1. C++ 构造函数：创建默认子对象，设置默认属性和默认附件关系。  
2. `PostSpawnInitialize`：Actor Spawn 后设置 World/Owner/Instigator/Role 等基础状态，并处理默认组件创建通知和注册。  
3. `FinishSpawning`：执行 Construction Script / `OnConstruction`，让蓝图构造逻辑和组件结构完成。  
4. `PostActorConstruction`：进入运行时初始化流程。  
5. `PreInitializeComponents`：Actor 在组件初始化前的回调。  
6. `InitializeComponents`：调用需要初始化的 Component 的 `InitializeComponent`，并处理自动激活等。  
7. `PostInitializeComponents`：Actor 在组件初始化完成后的回调。  
8. `BeginPlay`：游戏真正开始时调用，通常适合启动 Gameplay 逻辑。  
9. `Tick`：需要开启 Tick 时每帧执行。  
10. `EndPlay` / 销毁相关回调：关卡切换、Destroy、游戏结束等原因导致 Actor 结束播放并清理。  

### 组件生命周期补充
默认组件常见顺序可以这样记：

1. Actor 构造函数中 `CreateDefaultSubobject` 创建默认组件。  
2. 用 `SetupAttachment` 设置未注册组件的默认附加关系。  
3. Spawn/加载后组件进入注册流程，`RegisterComponent` 让它有 World，并创建渲染/物理等运行时表现。  
4. 如果组件设置了 `bWantsInitializeComponent`，会在初始化流程中调用 `InitializeComponent`。  
5. 如果组件允许并启用自动激活，则会 `Activate`。  
6. Actor `BeginPlay` 时，组件也会进入 BeginPlay 相关流程。  

### 更好的面试表达
Actor 的构造函数只负责默认对象结构和默认值。Spawn 后，UE 会做 `PostSpawnInitialize`，注册默认组件，并在 `FinishSpawning` 中执行 Construction Script / `OnConstruction`。随后 `PostActorConstruction` 会进入运行时初始化，依次走 `PreInitializeComponents`、组件的 `InitializeComponent`、`PostInitializeComponents`，最后在 World 开始 Play 后触发 `BeginPlay`。Component 不是只“跟着 Actor 构造”这么简单，它还要注册到 World，才会拥有渲染、物理、Tick 等运行时表现。

### 需要补充
- `CreateDefaultSubobject` 创建的是默认子对象，会参与 CDO/默认对象结构；它不是运行时动态创建组件的常规工具。
- 运行时添加组件通常用 `NewObject<UActorComponent>(Owner)`，Outer/Owner 要合理。

- 如果是 `USceneComponent`，还要处理附加关系：未注册时可 `SetupAttachment`，运行时已注册时通常用 `AttachToComponent` 并指定 `FAttachmentTransformRules`。

### 动态添加组件示例
```cpp

MeshComp->SetupAttachment(RootComponent);
MeshComp->RegisterComponent();
```
