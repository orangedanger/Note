## 1. RAII 和智能指针

### 我现在容易卡的点
- 容易把 RAII 说成“释放内存”，但 RAII 管的是资源，不只是内存。
- 容易忽略 RAII 的核心不是手动释放，而是对象生命周期和资源生命周期绑定。
- 容易把普通 C++ 智能指针和 UE 的 UObject 生命周期混在一起。

### 正确理解
- RAII 是 Resource Acquisition Is Initialization：资源获取即初始化。
- 对象构造时拿到资源，对象析构时自动释放资源。
- 资源可以是内存、锁、文件句柄、网络连接、GPU 资源等。
- RAII 的价值是让异常、提前 return、分支退出时也能自动清理资源。

### 面试表达
RAII 是 C++ 管理资源的核心方式。它把资源生命周期绑定到对象生命周期上：构造函数获取资源，析构函数释放资源。这样即使函数中途 return 或抛异常，只要栈对象离开作用域，析构函数就会自动执行，资源也能被正确释放。智能指针、`std::lock_guard`、`std::unique_lock` 都是典型 RAII 用法。

### 最小例子
```cpp
void UpdateSharedData()
{
    std::lock_guard<std::mutex> Lock(Mutex);
    SharedValue += 1;
} // 离开作用域时 Lock 析构，自动解锁
```

### 智能指针选择
- `std::unique_ptr<T>`：独占所有权，不能拷贝，只能移动。
- `std::shared_ptr<T>`：共享所有权，通过引用计数管理普通 C++ 对象。
- `std::weak_ptr<T>`：弱引用，不增加引用计数，常用于打破循环引用。
- UE 中的 `UObject` 不用 `std::shared_ptr` 管生命周期；成员引用通常用 `UPROPERTY() TObjectPtr<UObjectType>` 让 GC 能识别。

### 自测问题
- 为什么 `std::lock_guard` 能避免忘记解锁？因为它是RAII的用法，在构造时进行加锁，析构时会进行解锁，当 上的锁离开了作用域，这个锁就会被析构，就会解锁
- 为什么 `UObject` 成员不应该用 `std::shared_ptr` 管生命周期？因为UObject成员的声明周期由UE的GC进行管理，如果用shared_ptr，尽管仍然有计数但因为GC的root集被标记PendingKill那么不管shared_ptr是否有计数这个UObject对象都会被回收

## 2. 移动语义

### 我现在容易卡的点
- 容易把移动语义只说成“减少临时变量拷贝”，范围偏窄。
- 容易把 `std::move` 说成“执行移动”，但它本身只做类型转换。
- 左值/右值表达还不够稳，容易只说“命名/未命名”。

### 正确理解
- 移动语义用于减少昂贵拷贝，并表达资源所有权转移。
- 对持有堆内存、文件句柄、数组缓冲等资源的对象来说，移动通常只是转移内部指针或句柄，而不是复制整份资源。
- `std::move` 本身不移动资源，它只是把表达式转换成右值引用，让移动构造或移动赋值有机会被调用。
- 移动后的源对象仍然有效，但状态通常不应该依赖；它必须能被安全析构，也可以被重新赋值。

### 面试表达
移动语义解决的是昂贵拷贝和资源所有权转移问题。拷贝是复制一份资源，移动是把资源从一个对象转交给另一个对象。`std::move` 本身不做资源转移，它只是把一个表达式转换成右值引用，真正转移资源的是移动构造函数或移动赋值运算符。移动后源对象仍然是有效对象，必须能安全析构，但它里面的具体值通常不应该再依赖。

### 最小例子
```cpp
class FBuffer
{
public:
    explicit FBuffer(int32 InSize)
        : Size(InSize), Data(new int32[InSize])
    {
    }

    ~FBuffer()
    {
        delete[] Data;
    }

    FBuffer(FBuffer&& Other) noexcept
        : Size(Other.Size), Data(Other.Data)
    {
        Other.Size = 0;
        Other.Data = nullptr;
    }

private:
    int32 Size = 0;
    int32* Data = nullptr;
};
```

### 追问补答校准
你的补答方向是对的：移动后原对象没有销毁，所以仍然会析构。

更完整的表达是：移动只是转移资源，不是销毁源对象。源对象仍然会走析构函数，所以移动构造/移动赋值必须把源对象调整到一个可析构的状态，例如把裸指针置为 `nullptr`，避免两个对象析构时释放同一份资源。

### 自测问题
- `std::move` 为什么不等于“立刻移动资源”？std::move只是将表达式强行转为为右值引用，需要移动构造或移动赋值去实现移动资源
- 移动构造里为什么通常要把源对象指针置空？因为源对象仍然需要进行正常的析构如果源对象指针不置为空则会导致，析构时源对象指针仍然指向移动后的对象从而进行内存的释放导致移动后的对象部分参数被释放

## 3. 对象切片

### 我现在容易卡的点
- 已经知道按值传递会切掉派生类部分，但还需要补一句“多态行为会丢失”。
- UE 语境里容易写成 `AActor`/`UObject` 按值传递，但它们本来就不应该按值复制。

### 正确理解
- 对象切片发生在派生类对象按值传递或赋值给基类对象时。
- 新的基类对象只保存基类子对象，派生类新增成员和真实动态类型信息会丢失。
- 对象切片通常不会立刻崩溃，但会让多态失效，逻辑悄悄变错。
- 避免方式：多态对象使用指针、引用或合适的智能指针传递。

### 面试表达
对象切片是指把派生类对象按值传递或赋值给基类对象时，只拷贝了基类子对象，派生类新增的数据和真实动态类型被丢掉。这样通常不会崩溃，但会让虚函数多态失效。要避免切片，多态对象不要按值传递，应该使用 `Base*`、`const Base&` 或智能指针。

### 最小例子
```cpp
class FWeapon
{
public:
    virtual ~FWeapon() = default;
    virtual void Fire() {}
};

class FRifle : public FWeapon
{
public:
    virtual void Fire() override {}
    int32 Ammo = 30;
};

void UseWeapon(FWeapon Weapon) // 会发生对象切片
{
    Weapon.Fire();
}

void UseWeaponFixed(const FWeapon& Weapon) // 保留多态
{
    Weapon.Fire();
}
```

### 追问补答校准
你的补答里写 `void foo(ABase base);` 这个方向是对的，它表达了“按值接收基类对象”。

更规范的写法可以是：

```cpp
void UseWeapon(FWeapon Weapon);      // 错误：按值传递，可能切片
void UseWeapon(const FWeapon& Weapon); // 正确：引用传递，保留多态
void UseWeapon(FWeapon* Weapon);       // 也可以：指针传递，调用前检查 nullptr
```

如果是 UE 的 `AActor`/`UObject`，一般不要写成按值传递，而是写：

```cpp
void UseActor(AActor* Actor);
void UseObject(UObject* Object);
```

### 自测问题
- 为什么 `TArray<Base>` 存派生类对象会有切片风险？因为这里存储方式是按值存储，导致如果存储派生类对象会使得派生类新增变量不会被存储且多态不会生效
- `const Base&` 为什么能避免对象切片？因为他传递的是地址，而不是单纯的值，地址还是派生类开辟的地址，所有一些派生类新增的变量和多态能正常使用

## 4. 虚析构

### 我现在容易卡的点
- 容易把风险说成“派生类析构时不会调用基类析构”，这个说反了。
- 正常析构派生类对象时，顺序是先派生类析构，再基类析构。
- 真正风险是：通过基类指针删除派生类对象时，如果基类析构不虚，派生类析构可能不会被调用。
- `= default` 不是为了让派生类自动生成析构函数，而是告诉编译器生成默认析构实现，同时保留 `virtual` 语义。

### 正确理解
- 如果一个类用于多态，且可能通过基类指针删除派生类对象，基类析构函数必须是 `virtual`。
- 否则 `Base* Ptr = new Derived; delete Ptr;` 时可能只调用基类析构，不调用派生类析构。
- 结果是派生类自己的资源无法释放，并且这种行为属于未定义行为风险。
- `virtual ~Base() = default;` 表示析构函数是虚函数，但实现使用编译器默认生成的版本。

### 面试表达
多态基类通常要写虚析构，因为调用方可能持有 `Base*` 指向 `Derived` 对象并通过基类指针删除它。如果基类析构函数不是 `virtual`，`delete BasePtr` 时可能不会调用派生类析构，导致派生类资源泄漏或未定义行为。写成 `virtual ~Base() = default;` 可以保证析构从真实动态类型开始，先执行派生类析构，再执行基类析构，同时析构实现交给编译器默认生成。

### 最小例子
```cpp
class FBase
{
public:
    virtual ~FBase() = default;
    virtual void Tick() {}
};

class FDerived : public FBase
{
public:
    ~FDerived()
    {
        // 清理派生类自己的资源
    }
};

void Destroy()
{
    FBase* Ptr = new FDerived();
    delete Ptr; // 因为 FBase 析构是 virtual，会先调用 FDerived::~FDerived，再调用 FBase::~FBase
}
```

### 追问补答校准
你的补答已经抓到重点：如果不写虚析构，可能不会调用派生类析构。

需要修正的是两点：
- 不要说“基类引用派生类对象发生析构”，更准确是“通过基类指针删除派生类对象”。
- `= default` 的含义不是“让派生类自动生成析构函数”，而是“当前这个析构函数使用编译器默认实现”。

### 自测问题
- 为什么问题是“派生类析构没被调用”，不是“基类析构没被调用”？因为你用的是基类指针指向派生类对象，这是你的基类指针对象要被销毁，且析构不是多态，那么就不会调用派生类的析构函数，只能找到基类的析构函数
- 如果一个基类有虚函数但永远不会通过基类指针删除对象，是否一定要虚析构？面试中应该怎么回答？可以不用虚析构，但这样使用不能确保不会用基类指针删除对象，最好写成virtual ~ABase() = default;的格式

## 5. 当前 5 个仍不稳的问题
- `std::move` 本身不移动资源，这句话要能自然说出来。
- 移动后对象仍然有效，但状态不应依赖，要能解释“有效”和“状态未指定”的区别。
- 对象切片要补上“多态行为丢失”，不要只说“派生类部分没了”。
- 虚析构要明确风险是“派生类析构没被调用”。
- `= default` 的含义要说清楚：默认实现，不是给派生类生成析构。
