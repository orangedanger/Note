## A 组：反射、蓝图暴露、UHT、复制
- [x] `BlueprintCallable` 和 `BlueprintPure` 都能出现在蓝图里，它们对执行引脚有什么区别？BlueprintCallable他需要执行引脚，而BlueprintPure不需要
- [x] 一个类只加 `BlueprintType`，不加 `Blueprintable`，它还能被蓝图继承吗？不能`BlueprintType`是蓝图可以使用该类做属性，如果需要创建蓝图子类需要加Blueprintable
- [x] 数据对象类只想被蓝图变量引用，不想被蓝图继承，优先选哪个？`BlueprintType`
- [x] 一个 Actor 类通常为什么会同时需要 `Blueprintable` 和 `BlueprintType`？因为这个类通常需要创建蓝图放置在场景中，且可能需要其他地方引用
- [x] `.generated.h` 和 `GENERATED_BODY()` 分别解决什么问题？`?`我只知道UHT需要他们，GENERATED_BODY()是一些宏，被UHT识别后会扩展一些函数和代码到.gen文件,.generated.h则是引用那个生成的.gen文件让一些生成的函数能够被正常调用如 RPC的XXX_Implementation函数
- [x] `UPROPERTY(EditAnywhere)` 会不会改变 GC 行为？不会，GC只要加上UPROPERTY()这个变量就被标记为GC，加上EditAnywhere只会让这个变量可以在编辑器显示且修改
- [x] `UPROPERTY()` 对 `float` 和对 `TObjectPtr<UObject>` 的意义有什么不同？`?` UPROPERTY()对float主要是属性复制,编辑器显示，蓝图引用的一些功能，而TObjectPtr<UObject>多一个GC
- [x] `Replicated` 和 `ReplicatedUsing` 的区别是什么？后者需要绑定一个UFUNCTION函数，只要属性发生了变化就会调用后者绑定的函数
- [x] 为什么客户端本地改一个 replicated 属性通常不会同步给服务器？因为属性同步只发生在服务器到客户端，而不会发送给服务器
- [x] `GetHealthPercent()` 更适合 `BlueprintCallable` 还是 `BlueprintPure`？`BlueprintPure`因为他一般只需要提供HealthPercent
- [x] `ApplyDamage()` 为什么不适合写成 `BlueprintPure`？`?`一般作为BlueprintPure都比较轻，直接return一个结果的，而ApplyDamage一般在函数内需要执行逻辑.
- [x] `UFUNCTION()` 但不加 `BlueprintCallable` 的函数能不能被 `AddDynamic` 绑定？可以，AddDynamic只需要能够在反射系统中找到对于的函数就能完成绑定，不需要蓝图能调用
- [x] 普通 C++ 委托和动态委托在性能和蓝图支持上有什么区别？普通C++委托毫无疑问比动态委托性能上更强，因为普通C++委托更轻，但是普通C++委托不能在蓝图调用或实现一些功能，而动态委托可以在蓝图中调用，Assign或者Bind
- [x] `.generated.h` 不是最后 include 时，更可能是 UHT 错误还是普通运行时错误？UHT 错误，构建.gen时出现错误，因为缺少一些参数的引用
- [x] `UPROPERTY(TMap<int32, UObject*>)` 这类写法报错时，你会先查 UHT 规则还是查运行时逻辑？UHT 规则,这UPROPERTY()里面怎么能填TMap？？？

## B 组：GC、UObject 引用、指针语义
- [x] `UPROPERTY() TObjectPtr<UObject>` 和单独 `TObjectPtr<UObject>` 的区别是什么？前者在使用过程中更安全不会被突然垃圾回收，被反射系统支持。
- [x] 为什么 `TSharedPtr<UMyObject>` 这种写法在 UE 里通常是错误方向？因为TSharedPtr不是对Object类使用的，他是对普通C++指针使用的不适配
- [x] `UPROPERTY()`、`AddToRoot()`、`FGCObject::AddReferencedObjects()` 分别适合解决什么场景？`?`后面两个没见过，前者一般在.h文件对一些不想直接被回收的变量使用
- [x] 为什么局部变量 `UObject* Obj = NewObject<UMyObject>();` 在一次函数调用里通常没问题，但把 `Obj` 存成无 `UPROPERTY` 成员就有风险？如果只是一次函数调用中那么出了这个函数这个指针的使命就结束了，出了作用域就被回收了，但如果存成无 `UPROPERTY` 成员，他在使用过程中突然被回收了，那我只会调用就会出错
- [x] `FVector` 不需要 GC 的原因是什么？首先FVector就不是指针，他是个Struct，所以不需要担心他被回收
- [x] `FVector` 和 `UStaticMeshComponent` 在生命周期管理上最大的区别是什么？`UStaticMeshComponent`需要UE的GC保护防止被回收,而FVector不需要
- [x] C++ 父类默认值和蓝图子类默认值冲突时，实例通常以哪个为准？蓝图子类默认值会覆盖C++父类默认值，在那个蓝图子类中
- [x] 为什么 `AddToRoot` 不应该作为日常默认方案？`?`如果作为日常使用默认方案可能导致一些东西不被回收，导致一些应该被回收的东西没被正常回收
- [x] `Outer` 合理是否等于一定不会被 GC？为什么？`?`首先Outer合理是指这个Outer在头文件中被UPROPERTY()的TObject<XXX>所引用吗，如果这样他就使用了UE的GC功能，仍然在特定时间被GC，比如这个Outer的类对象被GC了，那这个就需要被GC

## C 组：对象创建、组件注册、生命周期
- [x] `OnConstruction` 和 `BeginPlay` 分别适合放什么逻辑？前者放一些创建默认子对象，位置附加，默认值初始化，后者放一些委托的绑定，定时器一些游戏正常的逻辑
- [x] 为什么组件创建了但没注册时，可能看不到、Tick 不起来或没有碰撞表现？`?`，我觉得你没有注册就不能附加到一个Actor中，那自然所有的功能不会被激活
- [x] `SetupAttachment` 和 `AttachToComponent` 的使用时机有什么区别？`SetupAttachment`一般使用在构造中，`AttachToComponent`则在游戏运行过程中创建时进行附加，不知道为什么?
- [x] `NewObject<UStaticMeshComponent>(this)` 后为什么只设置变量还不够？因为组件还需要进行注册和附加才能正常使用
- [x] 已经注册到 World 的组件，运行时更常用 `SetupAttachment` 还是 `AttachToComponent`？`AttachToComponent`
- [x] `SpawnActorDeferred` 适合解决什么问题？它和“在构造函数里 Spawn”有什么区别？适合做一些值的默认设置，比如你可能需要他设置一个参数但如果在构造之后执行又太晚了，我不理解什么叫在构造函数里 Spawn？
- [x] 组件创建后不 `RegisterComponent()`，最直观的问题是什么？`?`不知道可能是这个组件不会生效
- [x] `SpawnActor` 和 `NewObject` 最大的语义区别是什么？前者是对Actor进行Spawn后者是对Object进行Spawn，前者需要Transform，而后者不需要
- [x] 如果怀疑是碰撞导致 Spawn 失败，你会检查哪个 Spawn 参数？CollisionHandlingOverride
- [x] 如果逻辑只依赖自己组件初始化完成，不依赖其他 Actor，放 `PostInitializeComponents` 还是 `BeginPlay` 更合适？`PostInitializeComponents`不需要等其他的Actor生成就可以自己先实现
- [x] 如果逻辑依赖 PlayerController/Pawn possession，`BeginPlay` 一定够吗？不一定，可能Controller还没有附加，建议放在Controller的Possess后，或者Tick检查，加委托啥的
- [x] 如果两个场景 Actor 必须互相引用，你会用编辑器暴露引用、Tag 查找，还是 Subsystem 注册？分别有什么风险？`?`Subsystem 注册，首先第一个编辑器暴露引用会导致两个Actor的耦合比较深，Tag查找则相当于对所有人暴露了这两个Actor的信息，Subsystem注册最安全，两个Actor通过Subsystem互相访问进行解耦
- [x] 如果必须引用场景里的另一个 Actor，构造函数、`BeginPlay`、编辑器可配置引用三种方式你怎么选？首先如果我这个Actor也是提前放在场景里的Actor那么我会选编辑器可配置，如果不是是我在游戏过程中生成的，那么我会放在BeginPlay

## D 组：组件化、UI、技能/战斗通信
- [x] 如果 UI 销毁了但仍然绑定着 `HealthComponent` 的事件，可能出现什么问题？委托正常需要在EndPlay时Remove，如果仍然绑定，那么当Health变化时Broadcast会导致指针悬挂，因为委托本质是函数指针，它执行的是野地址

- [x] `HealthComponent` 应该暴露 `SetHealth` 给所有外部系统随便调用吗？不应该，正常应该，不可能直接给所有系统使用，肯定需要限制的，乱用会有问题，管理会混乱，且生命值的修改应该只在服务器上权威修改，不然同步也会出问题

- [x] “技能消耗蓝量”应该由 `SkillComponent` 直接扣 Health/Mana，还是发请求给 `AttributeComponent`？为什么？肯定是后者，否则Component的职能紊乱，Skill就应该只负责技能相关的逻辑，而不是属性的扣除，Skill应该是调用接口/委托的地方而不是直接扣除属性

- [x] 如果 `CombatComponent` 监听 `SkillComponent` 的委托，解绑应该放在哪里？CombatComponent的EndPlay函数

- [x] 写一条流程：`SkillComponent -> CombatComponent -> HealthComponent -> UI`，每个组件只写自己的职责。
  比如我有一个火球技能
  首先玩家按下某个绑定的键位这个按键从PlayerController会到InputManager做处理发送广播
  SkillComponent收到了这个广播做这个技能需要的准备比如判断技能是否能够释放，如果能够释放则开始技能的流程，发送一个通知 开始火球技能
  CombatComponent收到这个通知就从表格中获取这个技能相关的表现层的资产如 动画Montage，特效，mesh，一些AbilityInfo(伤害，速度什么的)将这些资产组合，并生成火球和动画的播放

  当火球命中之后会造成伤害会调用对方的HealthComponent做伤害处理
  我会在伤害结算时将需要的数值广播出去
  UI收到这个广播做出对应变化

## E 组：C++ RAII 和智能指针追问
- [x] 如果不用 `lock_guard`，手写 `lock()` / `unlock()`，遇到中途 `return` 会有什么风险？导致数据没有unlock()，不遵守RAII，数据没有正常释放，内存泄漏
- [x] `std::unique_lock` 和 `std::lock_guard` 都是 RAII，它们有什么使用差异？因为在他们构造时都会获取数据，析构时释放数据，完美遵守RAII，但不知道什么差异
- [x] 为什么 `std::unique_ptr` 能让 `new` 出来的对象也具备类似栈对象的自动释放效果？智能指针，遵循RAII，构造时获取资源，析构时释放资源
- [x] 析构函数里适合抛异常吗？为什么？不知道什么叫抛异常
- [x] 父节点持有子节点、子节点回指父节点时，哪个方向更适合用 `weak_ptr`？子节点指回父节点，需要方向统一
- [x] `weak_ptr.lock()` 返回空说明什么？说明weak_ptr监听的数据被释放了
- [x] `UPROPERTY() TObjectPtr<T>` 和 `TWeakObjectPtr<T>` 在“是否保持对象存活”上有什么区别？有，后者不会保持对象的存活，只是长时间观察对象不管对象是否存活所有需要用.IsVaild判断
- [x] 为什么 `TSharedPtr<UObject>` 可能和 UE GC 的生命周期管理冲突？因为TSharedPtr是对普通C++类型使用它是智能指针通过引用计数管理生命周期，但是UObject如果接入了反射系统他有自己的生命周期自然会冲突
